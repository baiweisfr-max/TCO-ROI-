1 导言:Claude Code 是什么

在动手之前,先建立一个准确的认知:Claude Code 是一个"会用工具的智能体",而不是一个聊天框。

Claude Code 是 Anthropic 官方的命令行编码智能体(agentic coding tool)。它运行在你的终端里,能够读写文件、执行命令、运行测试、调用外部工具,并在一个"读取 → 思考 → 调用工具 → 观察结果 → 继续"的循环中自主完成多步骤的工程任务。它也提供桌面端、Web 端(claude.ai/code)以及 VS Code / JetBrains 插件等形态。

它擅长什么

  • 跨文件的功能开发:理解现有代码风格后实现新功能、重构、修 bug。
  • 探索陌生代码库:快速回答"这个功能在哪实现""调用链是什么"。
  • 测试与验证:写测试、跑测试、根据失败迭代。
  • 自动化琐事:批量改写、生成样板、写提交信息、开 PR。
如何使用本教材 第 1–3 章建立基础认知;第 4–6 章是日常高频核心(记忆、上下文、工作流),建议反复实践;第 7–8 章是进阶扩展与团队治理;第 9–10 章是可随时翻阅的速查。每章结尾的 ✅ 正例 / ❌ 反例 对照是最值得带走的部分。

2 快速上手

五分钟跑通第一个任务,先有体感,再谈最佳实践。

安装与启动

# 全局安装(需要 Node.js)
npm install -g @anthropic-ai/claude-code

# 进入你的项目目录后启动
cd your-project
claude

首次启动会引导你完成登录认证。之后在交互界面里直接用自然语言下达任务即可。

三个最该先记住的输入前缀

前缀作用示例
/斜杠命令(内置或自定义)/init、/clear
@引用文件 / 资源(带路径自动补全)解释 @src/auth.ts
!进入 shell 模式直接执行命令!git status

第一条建议:先用计划模式探索

对不熟悉的代码库,启动后先按 Shift+Tab 切到 计划模式(plan),让 Claude 只读地探索并给出方案,再决定是否执行。详见第 6 章。

提示 打断很重要:任何时候按 Esc 可以中断 Claude 当前动作(上下文保留),立即纠偏;连按两次 Esc(或 /rewind)可回退到之前的对话/代码状态。

3 核心心智模型:上下文是稀缺资源

几乎所有 Claude Code 的最佳实践,都源于同一条约束。

"大多数最佳实践都基于一个约束:Claude 的上下文窗口会很快被填满,并且随着填满,性能会下降。上下文窗口是最重要的、需要被管理的资源。"
—— Claude Code 官方最佳实践文档

智能体工作循环

Claude Code 每一步都在做:读取你的指令与上下文 → 决定调用哪个工具(读文件 / 改文件 / 跑命令 / 搜索)→ 观察返回结果 → 继续下一步,直到任务完成。每一次工具调用的输入输出,都会占用上下文窗口。

由此推导出的三条铁律

  • 给它精准的上下文,而不是更多的上下文。无关信息会稀释关键指令,导致 Claude "忽略你真正想要的东西"。
  • 任务之间要清场。不相关的历史会拖累表现 —— 这就是 /clear 存在的理由。
  • 把可复用的项目知识沉淀到 CLAUDE.md,而不是每次重复打字。这就是第 4 章的主题。

4 CLAUDE.md 与记忆系统

CLAUDE.md 是你与 Claude 之间的"项目契约"。写好它,胜过每次重复解释。

CLAUDE.md 是一个特殊文件,Claude 在每次会话开始时都会读取它,并作为上下文(注意:是上下文,不是被强制执行的配置)。它适合放入构建命令、代码风格、工作流规则等"Claude 猜不到、但每次都需要"的项目知识。

4.1 放在哪里:记忆层级

Claude 会从启动目录沿目录树向上查找,并把发现的文件全部拼接进上下文(范围越具体的越靠后加载,从而优先级更高)。常用位置如下:

层级位置共享对象
企业 / 组织策略macOS:/Library/Application Support/ClaudeCode/CLAUDE.md
Linux/WSL:/etc/claude-code/CLAUDE.md
Windows:C:\Program Files\ClaudeCode\CLAUDE.md		组织内所有人
用户全局~/.claude/CLAUDE.md你自己,所有项目
项目(团队)./CLAUDE.md 或 ./.claude/CLAUDE.md团队(随源码提交)
项目(个人)./CLAUDE.local.md(记得加进 .gitignore)仅你,当前项目
加载行为 父目录的 CLAUDE.md 在启动时全量加载;子目录的 CLAUDE.md 则在 Claude 实际读取该目录文件时按需加载。这让你可以在 monorepo 的子包里放置局部规则。

4.2 用 /init 生成,用 /memory 维护

  • /init —— 分析你的代码库,自动生成一份包含构建命令、测试方式、项目约定的初始 CLAUDE.md。若已存在,则会提出改进建议而非覆盖。
  • /memory —— 列出当前会话加载的所有 CLAUDE.md / CLAUDE.local.md / 规则文件,可打开编辑。
  • 想追加内容,最简单的方式是直接对 Claude 说:"把这条加到 CLAUDE.md"。

4.3 用 @ 导入拆分文件

CLAUDE.md 可以用 @路径 语法导入其他文件,启动时一并展开加载(相对路径相对于该文件所在目录;最大递归深度 4 跳)。

See @README for project overview and @package.json for available npm commands.

# Additional Instructions
- git workflow @docs/git-instructions.md
- 跨 worktree 共享我的个人偏好 @~/.claude/my-project-instructions.md
注意 用 @ 拆分有助于组织结构,但不会减少上下文占用 —— 被导入的文件同样在启动时全部加载。控制体积的关键是"少写",不是"拆开写"。

4.4 该写什么、不该写什么

✅ 应该写
  • Claude 猜不到的 Bash 命令
  • 与默认不同的代码风格规则
  • 测试方式与首选测试运行器
  • 仓库规范(分支命名、PR 约定)
  • 项目特有的架构决策
  • 环境怪癖(必需的环境变量)与常见坑
❌ 不该写
  • Claude 看代码就能推断的内容
  • 语言的标准通用约定
  • 详尽的 API 文档(给链接即可)
  • 频繁变动的信息
  • 冗长的解释 / 教程
  • 逐文件的描述清单

4.5 黄金法则:保持精简

"保持精简。对每一行问自己:'删掉它会让 Claude 犯错吗?'如果不会,就删掉它。臃肿的 CLAUDE.md 会导致 Claude 忽略你真正的指令!"
  • 目标体积:每个 CLAUDE.md 控制在 200 行以内。越长越占上下文,遵循度越低。
  • 像对待代码一样对待它:出问题时回顾、定期裁剪;通过观察 Claude 行为是否真的改变来"测试"你的改动。
  • 可用 IMPORTANT、YOU MUST 等强调词提高关键指令的遵循度。
  • 把它提交进 git,让团队共同维护 —— 它的价值会随时间复利增长。
❌ 模糊

"Format code properly."
"Test your changes."

✅ 具体可执行

"Use 2-space indentation."
"Run npm test before committing."

5 上下文窗口管理

主动管理上下文,是把 Claude 用好与用废的分水岭。

5.1 /clear:任务之间清场

在两个不相关的任务之间,用 /clear 彻底重置上下文窗口。"漫长的会话里堆积的无关上下文会降低性能。"养成频繁 /clear 的习惯。

5.2 /compact:压缩而非清空

当接近上下文上限时,Claude Code 会自动压缩历史,把关键代码、文件状态和决策总结保留下来,腾出空间。你也可以手动并给出侧重:

/compact Focus on the API changes
提示 项目根目录的 CLAUDE.md 会在 /compact 后被重新从磁盘读取并重新注入;但子目录里的 CLAUDE.md、以及你没有主动调用过的技能,不会自动重新注入。

5.3 何时干脆开新会话

"如果你在同一个会话里就同一个问题纠正了 Claude 超过两次 …… 运行 /clear,用一个更具体的提示重新开始。一个上下文干净、提示更好的新会话,几乎总是优于一个堆满纠正记录的长会话。"

典型场景:先在一个会话里把需求/方案讨论清楚,然后开新会话专门执行,让实现阶段拥有干净、聚焦的上下文。

5.4 用 @ 引用文件,而不是描述位置

❌ 描述位置

"在 src 下面那个处理用户登录的文件里,大概在中间位置,有个校验函数……"

✅ 直接 @ 引用

看看 @src/auth/validateLogin.ts 的边界情况
(Claude 会在回应前先读取该文件)

5.5 善用子代理隔离上下文

让子代理(subagent)去做大范围调查 —— 它在独立的上下文窗口里工作,只把结论摘要返回给主会话,从而避免主上下文被探索过程的噪音填满。例如:"use subagents to investigate X"。详见 7.3。

6 工作流与计划模式

好的工作流不是限制,而是让 Claude 少走弯路、让你少做纠正。

6.1 推荐主流程:探索 → 计划 → 编码 → 提交

  1. 探索(Explore):进入计划模式,让 Claude 只读地阅读文件、回答问题,不做任何修改。
  2. 计划(Plan):让它给出一份详细的实现方案。可按 Ctrl+G 在编辑器里直接修改这份计划。
  3. 编码(Code):退出计划模式,让它对照方案实现,并自行验证。
  4. 提交(Commit):让它写一条描述性提交信息并开 PR,例如:commit with a descriptive message and open a PR。

6.2 计划模式(Plan Mode)

计划模式让 Claude "研究并提出改动,但不实际执行":它会读文件、跑命令来探索、写出计划,但不会修改你的源码。

操作方式
进入(循环切换模式)按 Shift+Tab 在 default → acceptEdits → plan 间循环
仅对单条提示生效提示前加 /plan
启动即进入claude --permission-mode plan
编辑计划Ctrl+G 在默认编辑器中打开方案修改
设为默认设置文件中 "permissions": { "defaultMode": "plan" }
何时该计划 "当你不确定方案、改动涉及多个文件、或你不熟悉所改代码时,计划最有用。如果你能用一句话描述这个 diff,那就跳过计划。"

6.3 测试驱动(TDD)协作

给 Claude 一个"能自我验证"的目标,质量会显著提升。让它先写测试、再写实现、然后跑测试并根据失败迭代。一个有效模式是"双 Claude":一个写测试,另一个写代码去通过这些测试。

❌ 模糊

给 foo.py 加点测试

✅ 具体 + 可验证

为 foo.py 写测试,覆盖"用户已登出"的边界情况。避免使用 mock。实现后运行这些测试。

明确反对 mock 做 TDD 时务必说明"避免 mock 实现",否则 Claude 可能写出能"骗过"测试的空壳实现。

6.4 视觉迭代工作流

对 UI 类任务:粘贴设计稿截图 → 让 Claude 实现 → 对结果再截图与原图对比 → 列出差异并修复。例如:"[粘贴截图] 实现这个设计。完成后对结果截图并与原图对比,列出差异并修复。"

6.5 通用最佳实践

  • 指令越精准,纠正越少。把边界情况、约束(如"避免 mock")直接写进提示。
  • 提供富内容:用 @ 引用文件、直接粘贴/拖拽图片、用 cat error.log | claude 把数据喂进来。
  • 尽早纠偏:Esc 中断、Esc Esc / /rewind 回退、直接说 "Undo that" 让它撤销。
  • 需要深度推理时,在提示中任意位置加入关键词 ultrathink。
关于"思考"关键词 当前官方文档中,只有 ultrathink 是被识别的关键词。早期博客里的 "think / think hard / think harder" 渐进式说法已不再是特殊关键词,会被当作普通文本。控制思考深度的主要方式是 /effort 等级(low / medium / high / xhigh / max)。

7 自定义扩展:命令 / Hooks / 子代理 / MCP

把重复的工作流固化成命令,把"每次都要做的事"交给 Hooks 自动触发,把专项任务拆给子代理,把外部系统接入 MCP。

7.1 自定义斜杠命令

把常用提示词存成 Markdown 文件,即可变成 /命令名 复用。

文档变化 官方已将"自定义命令"并入"技能(Skills)"体系:.claude/commands/deploy.md 与 .claude/skills/deploy/SKILL.md 都会创建 /deploy 且行为一致。你已有的 .claude/commands/*.md 仍然有效;下面的参数与字段语法对两者通用。
  • 项目级:.claude/commands/ · 个人级:~/.claude/commands/
  • 命令名 = 文件名(去扩展名)。输入 / 后跟名字调用。

参数占位符(注意:位置参数是 0 基的):

占位符含义
$ARGUMENTS调用时传入的全部参数
$ARGUMENTS[0] / $0第 1 个参数(0 基索引;$0 是第一个)
$1第 2 个参数,以此类推

常用 frontmatter 字段:description、argument-hint(自动补全提示)、allowed-tools(激活时免确认的工具)、model、disable-model-invocation。命令体内可用 !`命令` 在发送前注入 shell 输出。

---
name: fix-issue
description: 按编号修复一个 GitHub issue
argument-hint: [issue-number]
allowed-tools: Bash(git add *) Bash(git commit *) Bash(git status *)
---

当前改动:!`git diff HEAD`

请修复 issue #$0,遵循我们仓库的代码规范,并补充测试。

示例:/fix-issue 1234 会把 $0 展开为 1234,并在提示中注入实时的 git diff。

7.2 Hooks:在生命周期事件上自动触发

Hooks 让你在工具调用前后等时机自动执行命令(如自动格式化、拦截危险编辑),配置在 settings.json 中。

  • 配置位置:~/.claude/settings.json(全局)、.claude/settings.json(项目共享)、.claude/settings.local.json(项目个人,默认 gitignore)。
  • 常用事件名:PreToolUse、PostToolUse、UserPromptSubmit、Notification、Stop、SubagentStop、SessionStart、SessionEnd、PreCompact(实际事件集更大)。
  • matcher 按工具名匹配(支持正则与 | 或),如 Edit|Write、Bash、mcp__.*;大小写敏感。
  • 退出码:0 放行;2 阻断该动作并把 stderr 反馈给 Claude;其他码放行但记错。
  • /hooks 打开只读的 hooks 浏览器(增删改请直接编辑 JSON)。

示例 A:编辑后用 Prettier 自动格式化

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write" }
        ]
      }
    ]
  }
}

示例 B:用退出码 2 拦截对保护文件的编辑

// .claude/hooks/protect-files.sh
#!/bin/bash
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')
for pattern in ".env" "package-lock.json" ".git/"; do
  if [[ "$FILE_PATH" == *"$pattern"* ]]; then
    echo "Blocked: $FILE_PATH 命中保护规则 '$pattern'" >&2
    exit 2     # 退出码 2 = 阻断
  fi
done
exit 0

7.3 子代理(Subagents)

子代理是带 YAML frontmatter 的 Markdown 文件,正文即其系统提示。它在独立上下文窗口中工作,适合拆分专项、并行调查。

  • 位置:项目级 .claude/agents/ · 用户级 ~/.claude/agents/。
  • frontmatter:name 与 description 必填;tools、model 选填(省略 tools 则继承全部工具)。
  • /agents 打开管理界面(创建/编辑/删除,官方推荐方式)。
  • Claude 会根据 description 自动委派;在 description 里写上 "use proactively" 可鼓励主动调用。
---
name: code-reviewer
description: Reviews code for quality and best practices. Use proactively.
tools: Read, Glob, Grep
model: sonnet
---

You are a code reviewer. 分析代码并就质量、安全与最佳实践给出
具体、可执行的反馈。
子代理最佳实践 单一职责(每个只精于一件事)· 写详细的 description(Claude 据此决定委派)· 最小化工具权限 · 提交进版本库与团队共享。

7.4 MCP:接入外部工具与数据

MCP(Model Context Protocol)让 Claude Code 连接外部系统(GitHub、数据库、Notion 等)。

# 远程 HTTP 服务器(推荐)
claude mcp add --transport http notion https://mcp.notion.com/mcp

# 本地 stdio 进程(-- 之后是启动该服务器的命令)
claude mcp add --transport stdio airtable --env AIRTABLE_API_KEY=KEY \
  -- npx -y airtable-mcp-server
作用域存储位置团队共享
local(默认)~/.claude.json否(仅本项目)
project项目根 .mcp.json是(随版本库)
user~/.claude.json否(你的所有项目)
  • 管理:claude mcp list / get / remove;会话内用 /mcp 查看状态、完成 OAuth 登录认证。
  • 工具命名:mcp__<服务器>__<工具>(如 mcp__github__list_prs)。
  • 引用资源:@服务器:协议://路径,如 @github:issue://123。
安全 "连接前请确认你信任每个服务器。会抓取外部内容的服务器会带来提示注入(prompt injection)风险。" 出于安全,Claude Code 对来自 .mcp.json 的项目级服务器会先请求批准。

8 权限管理与安全

Claude Code 只拥有你授予的权限 —— 安全的最后一道防线是你对工具调用的审阅。

8.1 权限模式

模式无需询问即可执行适用
default仅读取起步、敏感工作
acceptEdits读取 + 文件编辑 + 常见文件系统命令你在边审边迭代代码时
plan仅读取(只探索、出方案)改动前先摸清代码库
auto全部,但有后台分类器做安全检查长任务、减少打断(预览特性)
dontAsk仅预先批准的工具锁定的 CI / 脚本
bypassPermissions全部(无任何确认)仅限隔离的容器 / 虚机

用 Shift+Tab 在 default → acceptEdits → plan 间循环;或启动时 claude --permission-mode plan;或在设置中 "permissions": { "defaultMode": "acceptEdits" }。

8.2 权限规则:allow / ask / deny

settings.json 中的 permissions 含三个数组,按 deny → ask → allow 顺序求值,首个匹配决定结果。

{
  "permissions": {
    "allow": ["Bash(npm run lint)", "Bash(npm run test *)", "Read(~/.zshrc)"],
    "deny":  ["Bash(curl *)", "Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"]
  }
}
  • 语法为 工具 或 工具(限定符),如 Bash(npm run test:*)、WebFetch(domain:*.example.com)、Edit、mcp__github__*。
  • 任一层级 deny,其他层级都无法 allow;权限规则跨作用域是合并而非覆盖。
  • /permissions 查看与管理所有规则及其来源文件。命令行可用 --allowedTools / --disallowedTools。

8.3 设置文件优先级(高 → 低)

  1. 企业托管设置(managed-settings.json,不可被覆盖)
  2. 命令行参数
  3. 项目个人:.claude/settings.local.json
  4. 项目共享:.claude/settings.json
  5. 用户:~/.claude/settings.json

8.4 危险旁路与安全审查

--dangerously-skip-permissions 等价于 --permission-mode bypassPermissions,跳过所有确认与安全检查。"仅在隔离环境(容器、虚机、无外网的 dev container)中使用",且它"对提示注入或意外操作不提供任何保护"。在 Linux/macOS 上拒绝以 root/sudo 启动。管理员可用 permissions.disableBypassPermissionsMode: "disable" 禁用它。
  • /security-review:扫描代码库中的漏洞(SQL 注入、XSS、认证/授权缺陷、不安全数据处理、依赖漏洞)并解释,可让 Claude 修复。
  • GitHub Action:anthropics/claude-code-security-review 在 PR 打开时自动审查并发表内联评论。
  • 你的责任:批准前审阅建议的代码与命令;别把不可信内容直接管道喂给 Claude;对关键文件的改动逐一核实;对外部服务的脚本放进虚机里跑。

8.5 团队协作规范

  • 把 ./CLAUDE.md、.claude/commands/、.claude/agents/、.claude/settings.json、.mcp.json 提交进版本库,让团队共享同一套约定。
  • 个人偏好放 CLAUDE.local.md / .claude/settings.local.json 并加入 .gitignore。
  • 组织级强制策略用企业托管设置下发,任何本地设置都无法覆盖。
